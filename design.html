01 Principles

The rules every later decision defers to.

  1. Documentation is standard OSS Rust, not a tutorial. //! module docs and /// on public items explain why; inline comments cover non-obvious decisions only. (v1 over-did this in src/llm/types.rs — v2 trims it back.)
  2. Pi is the reference, not the requirement. Adopt the parts of pi's design that teach something; simplify where pi is product-scale (providers catalog, OAuth, packages).
  3. The data model is the design. Sessions and events are plain JSONL you can cat, grep, and replay. Anything important is a serde type.
  4. Small surface. One binary, one provider protocol (OpenAI-compatible), one trait (Tool); no plugin code is loaded into the process — hooks (§22) are separate user-level processes. Deep trait hierarchies, macros, and unsafe are banned.
  5. Budgets keep it honest: ~150–300 lines per module; split when exceeded. Every commit keeps cargo test and cargo clippy clean (the existing review culture).
  6. Be permissive on the wire, strict internally. Providers are parsed loosely (unknown fields ignored); internal state is typed enums, not strings.

03 Extension research: pi, opencode 2, jcode, pi-durable

Requested in review: “do more research on extensions/plugins before confirming — if we get this architecture right, gg can evolve into anything.” Findings and the resulting decision.

projectmechanismlesson for ganggang
pi extensionsTS modules loaded into the agent process: event hooks, custom tools, commands, TUI components; distributed as npm/git packages.Maximal integration — but requires embedding a scripting runtime and trusting plugin code with everything the process can do.
opencode 2 pluginsnpm packages or local .ts/.js dirs declared in opencode.jsonc; lifecycle hooks (tool.execute.before/after, chat events); discovered from .opencode/plugins/.Same in-process model as pi; config-declared discovery is clean. Confirms hooks-over-events as the canonical surface.

pi-durableDurable conversation/task/document runtime for pi: runs checkpointed to pluggable stores (filesystem, postgres), resumable anywhere; companion tools (pi-env, pi-durable-agent) build on it.Durability is a storage concern layered over an append-only log — not a core-loop redesign. Ganggang's JSONL sessions are the same substrate.

Decision (v2)

  • No plugin runtime — one-shot hooks only (§22). The architecture keeps four seams so any of the above can be added later without rework:
    1. One event stream. Everything observable already flows through AgentEvent; a future plugin system could subscribe to it (and intercept before dispatch) — the pi/opencode shape. The shipped hooks (§22) are a separate, one-shot mechanism, not event subscribers.
    2. Tool trait + registry. Future dynamic tools (plugins, MCP) slot in as another Box<dyn Tool> source; the loop never changes.
    3. Append-only JSONL sessions. The durable base pi-durable builds on; checkpoint/resume is a storage upgrade, not a redesign.
    4. Self-dev falls out for free. Small Rust codebase + fast cargo build + persisted sessions = the model can evolve gg with its own tools today (jcode's bet, zero infra).
  • Hooks are the first shipped extension seam (v2.2, §22). User-level, one-shot shell commands at the loop's interception points, JSON in and out — no embedded runtime, no project-level declarations. It covers the stateless cases (guard, format, notify) without committing to a plugin API; the long-lived JSONL-over-stdio candidate above remains the path to custom tools and commands.
  • Candidate mechanism when needed: out-of-process plugins speaking JSONL over stdio — reuses the --mode json protocol verbatim, needs no embedded runtime, and isolates plugin crashes. Not decided; revisit deliberately.

04 Non-goals (explicit)

Written down so “not yet” never becomes “accidentally half-built”.

  • No plugin/extension runtime — hooks (§22) are one-shot shell commands, not an in-process API; no code is loaded into gg. Adding tools or commands still means editing Rust and rebuilding, which the agent itself can do.
  • No sandboxing or permission system. gg runs with the user's permissions; safety comes from where you run it (pi's stance, stated in our docs). A hook may deny a tool call, but that is user-authored workflow policy, not a sandbox.
  • No project-level executable resources: hooks are user-level only, so a cloned repository cannot add behavior before the model runs (§22).
  • No sub-agents, plan modes, or orchestration on top of the loop.
  • No cross-provider abstraction beyond the OpenAI-compatible wire types.
  • No Windows-specific tooling (POSIX bash assumed).
  • No performance work beyond “streaming renders promptly”.

05 Architecture

Three layers, mirroring how pi factored its TS monorepo (pi-ai / pi-agent / pi-coding-agent) — but as modules in one crate.

┌──────────────────────────── app layer ────────────────────────────┐
│  main.rs (clap CLI)   tui/ (ratatui)   printers (print, json)     │   interfaces
├──────────────────────────── agent layer ───────────────────────────┤
│  agent::loop_   context (system prompt)   skills   compaction     │   decisions
│  tools: read, bash, edit, write          session (JSONL io)       │
├──────────────────────────── llm layer ────────────────────────────┤
│  llm::types (wire)   llm::client (reqwest, timeouts, SSE later)   │   transport
└───────────────────────────────────────────────────────────────────┘
  • llm — exists today. Talks one protocol: OpenAI-compatible chat completions against GG_BASE_URL (Strata by default). Knows nothing about tools' meaning, sessions, or the loop.
  • agent — the harness proper. Pure decision logic + tool execution + session persistence. Testable without a network (mock server, §19). Depends on llm, never on tui.
  • app — CLI parsing, the TUI, print/JSON output. Consumes a single AgentEvent stream from the agent layer; never touches reqwest directly.

One turn, end to end (the whole system in one picture):

user input ──▶ session.append(user)
                  │
                  ▼
        context::build_request()          system = preamble + AGENTS.md + tools + skills
                  │                       history = active session entries → wire messages
                  ▼

                  │

The same agent core serves every interface — TUI, print, JSON. This is pi's most load-bearing property and costs nothing to keep.

08 Core data model

Three type families, deliberately separate: wire (what the provider sees), domain (what we store), events (what the UI sees). Pi makes the same split; conflating them is the classic harness bug.

1. Wire — llm::types (exists, grows)

ChatMessage, ChatRequest, ChatResponse as today. M2 adds the request's tools array (JSON-Schema function declarations). These stay stringly (role: String) on purpose: they mirror an external, evolving protocol.

2. Domain — agent::session

The source of truth. Typed, replayable, append-only. Conversion to wire messages happens per request, so domain types can be strict enums:

/// One entry in a session file. `id`/`parent_id` mirror pi's tree format;
/// v1 only ever appends a linear chain (parent = previous entry).
#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(tag = "type")]
pub enum Entry {
    Message { id: String, parent_id: Option<String>, ts: String, message: Message },
    Compaction { id: String, parent_id: Option<String>, ts: String,
                 summary: String, first_kept_id: String },
}

/// Domain message. Strict where the wire is loose: role is an enum,
/// tool arguments are parsed JSON (Value), not a string-in-a-string.
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct Message {
    pub role: Role,                       // User | Assistant | ToolResult
    pub content: Option<String>,
    pub tool_calls: Vec<ToolCall>,        // assistant only
    pub tool_call_id: Option<String>,    // tool results only
    pub usage: Option<Usage>,            // assistant only, for the footer
}

#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "snake_case")]
pub enum Role { User, Assistant, ToolResult }

The agent layer owns exactly one conversion function, to_wire(&[Entry]) -> Vec<ChatMessage>, plus its inverse for recording responses. All provider-shape knowledge lives in those two functions — the rest of the codebase never sees "function" objects or string-encoded arguments. This replaces the current main.rs pattern of pushing wire ChatMessages directly.

The domain ToolCall carries args: Value (parsed once at the boundary, in from_response) plus args_error: Option<String> — set when the provider's argument string was not valid JSON. A call with args_error is never dropped from replay (its tool_result references the id) and its arguments replay as {}, never as the invalid text.

3. Events — events.rs

/// Everything the outside world can observe. The TUI renders these;
/// `--mode json` serializes them; print mode prints the last AssistantText.
#[derive(Debug, Clone, Serialize)]
#[serde(tag = "type", rename_all = "snake_case")]
pub enum AgentEvent {
    RunStarted,
    TurnStarted,
    AssistantText { delta: String },     // streaming-era: chunks
    ToolCallStarted { name: String, id: String, args: Value },
    ToolCallFinished { name: String, id: String, output: String, is_error: bool },
    TurnEnded { stop_reason: String },
    RunEnded { turns: u32 },
    RunAborted,                          // terminal record of an aborted run
    Warned { message: String },          // truncation, compaction, bad args…
}

The agent layer emits events through a channel (tokio::sync::mpsc); interfaces subscribe. JSON mode is literally serde_json::to_line(event).

09 The agent loop

~60 lines of straight-line async. Everything else in the agent layer exists to feed it.

pub async fn run(&mut self, input: String, events: &mut Sender<AgentEvent>) -> anyhow::Result<()> {
    self.session.append_user(input)?;
    let mut turns = 0;

    loop {
        turns += 1;
        events.send(AgentEvent::TurnStarted).await?;

        let req = context::build_request(&self.session, &self.tools, &self.cfg)?;
        let resp = self.client.send(req).await?;           // existing client
        let msg = self.session.append_assistant(resp)?;    // records usage, tool_calls

        if msg.tool_calls.is_empty() {
            events.send(AgentEvent::TurnEnded { stop_reason: "stop".into() }).await?;
            break;
        }
        // Sequential, in order: deterministic, debuggable. (Parallelism = later, if ever.)
        for call in &msg.tool_calls {
            events.send(AgentEvent::ToolCallStarted { .. }).await?;
            let result = tools::dispatch(&self.tools, call).await;   // errors are VALUES
            self.session.append_tool_result(call.id.clone(), &result)?;
            events.send(AgentEvent::ToolCallFinished { .. }).await?;
        }
        events.send(AgentEvent::TurnEnded { stop_reason: "tool_calls".into() }).await?;
        // (M6: compaction check here, before next build_request)
    }
    events.send(AgentEvent::RunEnded { turns }).await?;
    Ok(())
}
  • Tool errors never abort the run. A failed tool call is recorded as an is_error result the model can react to. Only transport/session-io failures propagate with ?. (Already the documented contract in types.rs.)
  • No turn cap (review decision — pi has none either): a runaway loop is stopped by the user (Esc / Ctrl-C abort), not by a counter. The turns counter exists only for the RunEnded event and the footer.
  • Abort: a tokio_util::sync::CancellationToken (or plain Arc<AtomicBool>) checked between tool calls; on abort, synthesize is_error tool_results for the batch's unanswered calls (replay must never carry a dangling tool_call), append a marker, emit RunAborted, and return Ok. Esc in the TUI sets it.
  • Steering (later): the input side grows a queue; user messages submitted mid-run are appended after the current tool batch — pi's “steering” semantics. The loop shape above already has the seam (end of tool batch).
  • Hooks (§22): matching pre_tool hooks run after ToolCallStarted and before dispatch; a deny synthesizes an is_error result instead of running the tool. Matching post_tool hooks run after ToolCallFinished (the result is already recorded). run_end hooks run once before RunEnded, on a clean final answer only. Hook failures are Warned events and never abort a run; a deny is a normal tool error value. The runner polls the abort flag, so Esc also kills a running hook.

10 Tools

One trait, four implementations, plain values in and out. Pi's tool semantics, Rust-ified.

pub struct ToolResult { pub output: String, pub is_error: bool }

pub trait Tool: Send + Sync {
    fn name(&self) -> &'static str;
    fn description(&self) -> &'static str;
    /// JSON Schema for the `parameters` object of the function declaration.
    fn schema(&self) -> Value;
    /// Boxed future: `async fn` in traits is stable but not dyn-compatible,
    /// and one 10-line wrapper beats an macro dependency.
    fn execute<'a>(&'a self, args: &'a Value) -> BoxFuture<'a, ToolResult>;
}

pub struct Registry(Vec<Box<dyn Tool>>);

Dispatch never touches JSON-in-a-string: from_response parses call.function.arguments once at the boundary (empty string ⇒ empty object) and records parse failures as args_error on the domain call. Dispatch checks args_error first and returns an is_error tool result (“arguments were not valid JSON: …”) without invoking the tool — never a run failure, so the model retries correctly. Each tool then deserializes the parsed Value into its own args struct (serde, permissive defaults), reporting field errors the same way.

pre_tool hooks (§22) sit between ToolCallStarted and dispatch. A deny returns an is_error result exactly like a tool failure — the model reads it and adapts; the tool never ran. Hooks cannot rewrite arguments or invent results, so the assistant's recorded call and the tool result stay truthful. A hook runs with the same permissions and in the same cwd as bash; it is user-level policy, not a sandbox.

The four tools (pi semantics)

toolbehaviorguardrails

11 Skills

Core requirement. Implement the Agent Skills spec subset pi implements, so pi/Anthropic skills work unmodified.

  • Discovery (at startup): ~/.agents/skills/ then .agents/skills/ found walking cwd → ancestors, stopping at the repo root. Only directories containing SKILL.md (pi's portable form; standalone .md files not supported — noted divergence).

  • Loading: the model reads SKILL.md with the existing read tool when a task matches, then follows it (including bundled scripts via bash, resolved relative to the skill dir — the system prompt tells it how).
  • Forcing: /skill:<name> [args] in the TUI loads the instructions and appends them as a user message (pi's exact behavior). disable-model-invocation: true hides from advertising, command still works.
  • Collisions: first discovered wins, warning event (pi's rule).

12 Context assembly & system prompt

Built fresh for every request (cheap, no invalidation bugs), from named sections like pi:

13 Sessions

Pi's format, thinned. JSONL, append-only, one file per session.

  • The first format version is a linear chain — every entry's parentId is the previous entry. But the field exists, ids exist, so pi-style tree navigation (/tree, forking) can be added without a format migration. That's the entire reason they're there from day one.

  • Hooks never change the format. A pre_tool denial is a normal tool_result with is_error; hook failures are Warned events, not persisted (§22). The session header id is what the hook payload calls session_id.

14 Compaction

Designed now, built in M6 — pi's algorithm with pi's defaults.

  • Trigger: after a tool batch, before the next request: context_tokens > context_window − reserve (16,384). Context tokens from the last response's usage; estimate chars/4 only when the server reports none.
  • Cut point: walk back through entries accumulating tokens until keep_recent (20,000); snap to the preceding user-message boundary (pi's span rule — never orphan tool results from their assistant call).
  • Summarize: one extra LLM call: “summarize the conversation so far for continuation; preserve goals, decisions, file paths, open tasks” + the messages being dropped. Failure ⇒ warn and continue un-compacted (never kill the run).
  • Record & rebuild: append a compaction entry; from then on to_wire emits summary-as-user-note + entries from firstKeptId onward. Raw entries stay in the file (pi's invariant: compaction never destroys history).
  • Manual: /compact [instructions] same path with focus instructions.
  • context_window is config (GG_CONTEXT_WINDOW), default 131,072 (review: “context should be higher”). Set it to match strata launch --context, which takes 8k–256k.

15 Interfaces

One agent core, three front-ends. Interface choice mirrors pi: TTY ⇒ TUI; -p ⇒ print; --mode json ⇒ events.

TUI (ratatui, M4)

  • Fullscreen layout like pi: scrolling transcript / editor / one-line footer (dir, model, tokens, context %).
  • Transcript renders: user text, assistant text (markdown later), tool calls as collapsed ▸ bash git status lines expandable with Ctrl+O, warnings dimmed.
  • Keys (fixed, no config): Enter send · Alt+Enter / Ctrl+J newline (Shift+Enter where the terminal reports modified keys) · Ctrl+A/E line start/end · Ctrl+K/U kill to line end/start · arrows move the composer cursor · Esc abort run · Ctrl+O expand · Ctrl+X copy last answer · / commands · !cmd shell prefix (output enters context, like pi).
  • Commands: /new /resume /compact /skills /session /context /prompts /hooks /quit /skill:<name>. /skills lists discovered skills with paths — cheap, great for debugging discovery; /hooks lists loaded hooks (event, tools, timeout, command) or says hooks are disabled. A pre_tool denial renders as a failed tool line, like any other tool error.

Print mode (M2)

  • gg -p "explain the failing test" — progress to stderr (turn markers, tool lines), final assistant text to stdout, exit. Pipeable: git diff | gg -p "review" reads stdin into the prompt. Persists a session like every other mode; --no-session for throwaway runs.

JSON mode (M6)

  • gg --mode json "…" — session header then AgentEvents, one JSON object per line; same enum the TUI consumes, so the two can't drift. No RPC, no SDK. Hooks add no event variants: a denial is an ordinary ToolCallFinished with is_error, a hook failure a Warned (§22).

17 Error handling & robustness

  • anyhow everywhere for now — one error type, ? + .context(), already the house style. Upgrade path (thiserror enums in llm) is noted but not taken until a caller actually needs to match on variants.
  • Three failure classes, three policies: transport/IO ⇒ abort run with context (user retries); tool failure ⇒ value fed back to model; provider-shape oddities (no choices, empty content) ⇒ warn event + best effort (existing patterns in main.rs keep their comments).
  • Timeouts: existing client values (10 s connect / 300 s request) plus per-tool bash timeout. Everything that can hang has a number.
  • Every truncation or dropped call is visible: a Warned event, never a silent .unwrap_or_default() at the boundary.
  • Hooks degrade to warnings. A hook that crashes, times out, cannot spawn, or prints malformed output is a Warned event and the run continues (a pre_tool hook then allows the call — deliberate fail-open, since a broken guard must not wedge the agent). A deliberate deny is not an error: it is a normal is_error tool result. Hook processes get the bash timeout/group-kill discipline, and an abort kills a running hook (§22).
  • No retries in v1 — the local server is either up or it isn't. Revisit with streaming.

22 Hooks

User-defined shell commands at the loop's interception points — the first shipped extension seam (§03). One process per event, JSON on stdin, an optional decision on stdout. No runtime, no project-level code.

What a hook is

  • A one-shot command. gg runs bash -c <command> in the session cwd, writes one JSON object to stdin, closes it, and reads stdout/stderr to completion (bounded). Hooks live in the agent layer, so every interface gets them; no state survives between invocations.
  • Not a plugin runtime. No code is loaded into the process, no custom tools or commands, no TUI components. Custom tools still mean editing Rust (§03, §04).
  • Not a sandbox or an approval prompt. A hook runs with the user's permissions — the same trust boundary as the bash tool (§10). A pre_tool deny is user-authored policy, not a security boundary: the model already has bash, and the user can edit the file.
  • User-level only. Hooks are declared in ~/.gg/hooks.toml. A project .gg/hooks.toml is ignored with a startup warning, so cloning a repository cannot add executable behavior. Pointing a user-level command at a project script is allowed — the user wrote the command.

Configuration

# ~/.gg/hooks.toml — user-level policy, loaded once at startup
[[hooks]]
event = "pre_tool"                 # pre_tool | post_tool | run_end
tools = ["bash"]                   # tool events: omit or ["*"] for all; exact names
command = "~/.gg/hooks/guard-bash.sh"
timeout_secs = 5                   # default 10; must be positive

[[hooks]]
event = "post_tool"
tools = ["edit", "write"]
command = "./scripts/format-changed-file.sh"

[[hooks]]
event = "run_end"
command = "notify-send gg 'run finished'"
keyrequiredrule
eventyespre_tool, post_tool, run_end; anything else is a config error naming the valid set
toolsnotool events only; exact registry names or ["*"]/omitted for all; empty or unknown names are errors; forbidden on run_end
commandyesnon-empty; run with bash -c in the session cwd
timeout_secsnodefault 10; positive; the process group is killed at the deadline
  • An absent file means no hooks. A malformed or unreadable file is a startup error naming the path (the config.rs philosophy: invalid values are loud). Unknown keys are ignored, consistent with config and wire forward-compatibility.
  • Hooks load once per process (a --watch restart reloads them, like skills and prompt templates). The TUI factory reuses the same set across /new and /resume.
  • --no-hooks skips loading and the project-file warning entirely; /hooks lists what loaded, or says hooks are disabled.

Events and firing points

eventwhenmayfailure policy
pre_toolafter ToolCallStarted, before dispatchallow or deny (no rewrite)Warned + allow
post_toolafter ToolCallFinished; the result is already recordedobserve onlyWarned, run continues
run_endonce, after a clean final answer, before RunEndedobserve onlyWarned, run continues
  • Matching hooks run in file order, one at a time. The first pre_tool deny wins and the remaining pre hooks for that call are skipped; the tool never executes and no post_tool hook fires for it. Other calls in the batch still run.
  • A deny synthesizes ToolResult::err("denied by pre_tool hook: <reason>") — a normal tool error the model reads and reacts to. It is appended to the session like any result, so replay stays truthful.
  • post_tool runs after the result is recorded, so a slow formatter cannot change what the model was told. run_end fires for a clean final answer only; aborted and failed runs return before it.
  • No hooks fire for the compaction summarize call, the TUI's ! shell, skill loading, or prompt-template expansion — those are not model tool calls. A call whose provider arguments failed to parse also skips hooks: dispatch's args_error result is the answer, not a policy decision (§10).
  • The abort flag is polled while a hook runs (every 100 ms); Esc kills the hook's process group, the current call gets "aborted before execution", and the loop's existing abort path synthesizes the rest of the batch (§09).

Protocol

One JSON object on stdin. Every payload carries version (1), event, cwd, and session_id (null with --no-session). Tool events add the call; post_tool also carries the result the model saw:

{"version":1,"event":"pre_tool","cwd":"/home/hf/Projects/ganggang","session_id":"…",
 "tool":{"id":"call_339…","name":"bash","args":{"command":"git status"}}}

{"version":1,"event":"post_tool","cwd":"…","session_id":"…",
 "tool":{"id":"call_339…","name":"bash","args":{"command":"git status"}},
 "result":{"output":"[exit code: 0]\n…","is_error":false}}

{"version":1,"event":"run_end","cwd":"…","session_id":"…","turns":3}

Only pre_tool reads stdout, and only one decision is recognised:

{"decision":"deny","reason":"recursive delete outside the repo"}
hook ends withpre_toolpost_tool / run_end
exit 0, empty stdoutallowsuccess
exit 0, {"decision":"allow"} / {"decision":"deny","reason":"…"}explicit allow / denystdout ignored
exit 0, anything else on stdoutWarned + allowignored
non-zero exit, signal, timeout, spawn failureWarned + allowWarned
  • reason is optional and capped at 2 KiB; the default names the hook. Unknown fields are ignored; an unknown decision or invalid JSON is a failure, not a deny.
  • Failure is deliberately fail-open — a broken guard must not wedge the agent. The Warned names the hook and carries a bounded stderr tail. A guard that must fail closed should not be the only defence; there is no sandbox (§04).
  • stdout is capped at 64 KiB and stderr at 8 KiB, both drained past the cap so the child never blocks on a full pipe. A hook that ignores stdin is fine; a broken pipe on the stdin write is not a failure.
  • Hooks share the bash tool's process discipline: own process group, kill_on_drop, group-wide SIGKILL at the deadline (§10). A hook is sequential with the tool call it observes; there is no parallelism.
  • No new AgentEvent variants: a deny is a ToolCallFinished with is_error; a hook failure is Warned. JSON mode and print mode need no shape changes (§15).

Deliberate limits (v1)

  • No argument rewriting, synthetic results, or output injection. The recorded call and result must match what actually ran and what the model saw; rewriting would need a new session entry to stay honest. Revisit with an explicit hook entry type.
  • No "ask" decision. There is no approval UI; the model is either allowed or denied, and a denial is a value.
  • No regex matchers, per-run hook environment, chains, or parallel hooks. Exact tool names or *; sequential in file order.
  • No project-scoped hooks. They need a trust story (a startup prompt or a user-level allowlist), which is more surface than the feature is worth today. A user-level command can still point at a project script.
  • Still deferred: the long-lived plugin runtime. Custom tools, commands, and TUI components remain out of scope (§03, §04); hooks cover only the stateless cases.

Example: a guard

#!/usr/bin/env bash — ~/.gg/hooks/guard-bash.sh
cmd=$(jq -r '.tool.args.command // empty')
case "$cmd" in
  *"git push --force"*|*"rm -rf /"*)
    printf '{"decision":"deny","reason":"blocked by the user guard hook"}\n' ;;
esac
